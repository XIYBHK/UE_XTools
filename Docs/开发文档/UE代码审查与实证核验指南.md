# UE 代码审查与实证核验指南

本文用于 Unreal Engine C++ 项目和插件的代码审查。目标不是尽可能多地列出疑点，而是把每项结论收敛为可复现、可定位、可验证的工程事实。

## 1. 证据优先级

审查结论按以下顺序取证：

1. 当前工作树中的实现、声明和构建配置。
2. 完整调用链、调用方搜索和反射可达性。
3. 当前 `HEAD` 的提交历史与相关变更说明。
4. 支持版本对应的本机 UE 引擎源码。
5. Epic 官方文档。
6. 论坛、Issue、博客和其他网络资料。

网络资料只能提供检索线索。涉及引擎内部行为、模块归属、事务、反射派发、GC 或版本差异时，最终结论必须回到目标版本源码或可控运行时探针。

## 2. 审查前固定基线

开始审查前记录：

- `git rev-parse HEAD`；
- `git status --short`；
- 目标 UE 版本和构建目标；
- 本轮允许修改的模块与明确排除项；
- 已有测试和构建报告的位置。

工作树不干净并不妨碍审查，但必须区分用户已有改动与本轮改动。不要把旧二进制、旧日志或不同提交生成的报告当作当前代码证据。

## 3. 从现象闭合到调用链

每个问题至少回答以下问题：

1. 缺陷行是什么？
2. 哪个公开入口或引擎回调能到达它？
3. 仓库内有哪些真实调用方？
4. Blueprint、反射、资产或外部 C++ 是否也能到达？
5. 输入满足什么条件时触发？
6. 输出、状态或生命周期如何偏离契约？
7. 是否已有守卫、回退或后续自愈路径？

只看到可疑代码不足以判定缺陷。反之，零仓内调用也不等于可删除：导出符号、`UFUNCTION`、`USTRUCT(BlueprintType)` 和序列化资产都可能构成外部兼容面。

## 4. 严重度与处置分类

建议将结论分为以下类别：

| 类别 | 判定标准 | 典型处置 |
| --- | --- | --- |
| 正确性或安全缺陷 | 可构造输入使状态、结果、内存或生命周期违反契约 | 修复并补回归测试 |
| 性能缺陷 | 成本可复现且违反调用频率、复杂度或资源上界契约 | 优化并用计数或 Insights 验证 |
| 显式调用者契约 | 成本或限制已在 API 上说明，且有替代入口 | 保持现状，确保文档准确 |
| 维护债务 | 无错误输出，主要影响可读性、重复或一致性 | 独立维护批次处理 |
| 兼容面决策 | 删除或改签名会影响外部 C++、反射或资产 | 明确兼容策略后处理 |
| 误报 | 机理、可达性或引擎契约不成立 | 撤销并记录误判原因 |

不要用“理论上可能崩溃”替代具体触发链，也不要把有界微秒级成本直接定性为性能缺陷。

## 5. UE 专项核验方法

### 5.1 模块与 IWYU

- 头文件所在目录不等于链接模块归属；需要同时核对 `.Build.cs`、导出宏和引擎模块定义。
- Runtime 模块不得依赖 Editor 模块。
- `BuildPlugin -StrictIncludes` 比普通 Unity Build 更容易暴露隐式包含。
- 跨版本依赖变更应由目标版本构建矩阵裁决，不凭单一版本推断。

### 5.2 UObject、反射与接口派发

- 区分原生 C++、Blueprint 覆盖和未实现接口三条路径。
- 对 `Execute_*`、`ProcessEvent` 或 native thunk 的疑问，应检查 `UFunction` 绑定、调用空间和接口地址调整。
- 临时测试 World 必须完成被测 API 所需的初始化；未初始化 fixture 产生的异常不能归因于生产代码。
- 用运行时探针时记录函数地址、Owner Class、接口地址和实际回调计数，避免只观察最终计数后猜测断链点。

### 5.3 Editor 事务与变更通知

- `Modify()` 负责事务快照；`PreEditChange` 和 `PostEditChange` 还可能承担资源拆除、重建和广播。
- 不要仅凭函数名称要求机械配对。应对照目标 UObject 子类的覆盖实现和 Epic 同类工具的调用范式。
- 资产修改测试至少覆盖结果、包脏标记和 Undo/Redo；需要实时组件刷新的功能还要验证物理、导航或渲染状态。

### 5.4 生命周期和异步回调

- 跨帧、Ticker、TaskGraph 和工作线程回调不得捕获可能销毁的 UObject 裸指针。
- 使用 `TWeakObjectPtr` 后，必须在执行点重新解析并立即判空。
- Slate 所有权图要同时检查 Window 到 Content 的强引用和 Content 到 Window 的反向引用。
- 协程帧只能在满足标准前置条件时销毁；`resume()` 后不得假设帧仍然存在。

### 5.5 并发和原子状态转换

- 线程安全审查关注完整事务，而不只是单次容器读写。
- `读取 -> 计算 -> 写回` 必须由同一临界区覆盖，分别加锁仍可能丢更新。
- 明确锁顺序，搜索是否存在反向获取路径。
- UObject/Actor 的容器有锁不代表 Actor 操作可以离开游戏线程。

### 5.6 排序比较器

- 供 Sort/Heap/Partition 使用的比较器必须满足严格弱序。
- 浮点路径必须显式定义 NaN、正负无穷和正负零的语义。
- 升降序、null 元素和等价键稳定性要形成一致契约。
- 测试优先断言排序不变量；只有输出顺序属于公开契约时才使用完整 golden。

### 5.7 缓存和性能

缓存设计必须同时回答：

- 键是否覆盖全部影响结果的输入？
- 失效条件是什么？
- 生命周期挂在哪个 World、对象或模块上？
- 是否跨 World 污染？
- 是否线程安全？
- 内存上界和淘汰策略是什么？
- 目标场景的实际命中率是否足以抵消治理成本？

如果这些问题没有答案，新增全局缓存通常不是合理修复。已有 `TRACE_CPUPROFILER_EVENT_SCOPE` 时，应优先用 Unreal Insights 量化，而不是根据循环次数猜测严重度。

## 6. 公共 API 的保留与删除

处理零调用公共类型时，按以下顺序判断：

1. 是否导出 C++ 符号？
2. 是否带 `UFUNCTION`、`UCLASS`、`USTRUCT` 或 `BlueprintType`？
3. 是否可能被项目资产序列化引用？
4. 是否已经发布并承诺兼容？
5. 是否存在质量合格的替代 API？
6. 保留是否产生运行时成本或行为变化？

尚未发布、未进入兼容承诺范围的初始构建，可以直接删除错误抽象并同步测试和文档。已经发布的反射类型通常需要弃用周期、迁移说明或资产重定向方案。不要把“仓库内零引用”当成唯一删除依据。

## 7. 确定性测试原则

修复验证应钉住行为，不以“编译通过”代替测试。

推荐方式：

- 概率逻辑注入固定随机源；
- 并发逻辑断言精确最终状态，不依赖线程调度顺序；
- 私有状态通过测试专用 friend 或派生类观察，不扩张生产 API；
- 异步路径使用 TaskGraph 冲刷、Latent Command 或显式状态等待；
- Slate 生命周期使用真实 `FSlateApplication` 和窗口销毁队列；
- NavMesh/AI 使用固定最小地图，先验证 fixture 再验证产品行为；
- 报告同时检查预期测试数、`failed`、`notRun`、`inProcess` 和 warnings。

详细做法见[《UE 全自动测试最佳实践》](../测试相关/UE全自动测试最佳实践.md)。

## 8. 常见误报来源

- 只读单个函数，未搜索完整调用面。
- 使用旧行号、旧二进制或不同提交的测试产物。
- 根据头文件路径猜模块依赖。
- 根据论坛描述推断引擎内部实现。
- 混淆 `ensure` 与 `ensureAlways`。
- 把局部变量、固定上限成本或明确 ToolTip 契约当成泄漏。
- 忽略 null、抽象类、未初始化 World 等 fixture 前置条件。
- 把“结果不稳定”夸大为越界或崩溃，却没有算法控制流证据。
- 为消除疑点引入比问题更复杂的全局缓存、兼容层或重复抽象。

## 9. 审查交付格式

每项发现至少包含：

- 结论分类与严重度；
- 当前代码位置；
- 入口和完整调用链；
- 触发条件与可观察后果；
- 引擎或标准契约证据；
- 最小修复范围；
- 确定性测试边界；
- UE 支持版本风险；
- 本轮是否实际修改、构建和提交。

报告结束时只列仍需行动的事项。已经修复、撤销或明确维持现状的历史流水，应归入 Git 历史和变更日志，不应长期占据当前任务清单。
